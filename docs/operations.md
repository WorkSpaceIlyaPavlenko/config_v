# Эксплуатация и восстановление

## Что подготовлено

Генератор создаёт пару X25519 для REALITY, случайный shortId, отдельный UUID устройства, серверный JSON, Caddyfile и клиентский профиль. Файлы `runtime/` имеют права 0600, каталоги 0700. Они не выводятся в терминал и исключены из Git.

Docker endpoint задаётся явно. Локально разрешён только socket профиля Colima `config-v`; удалённо — `ssh://user@host`. Переменные глобального Docker context и Terraform CLI overrides очищаются. Отключать проверку SSH host key нельзя. Пользователь с доступом к обычному rootful Docker API имеет значительные права на VPS, даже если процессы контейнеров запускаются без root.

Конфигурация передаётся через stdin в отдельные тома; никаких приватных ключей в Terraform `env`, `upload`, variables или state. Caddy не получает том с приватным ключом Xray. Обновление сначала проходит проверки в временных томах. Сервисные контейнеры работают с UID 65532, read-only корнем и без Linux capabilities; временным установочным контейнерам нужны только описанные в коде права на их собственные тома.

## Что означает проверка

- `vpn:validate`: соответствие клиентских и серверных параметров, форма конфигурации; не заменяет парсер Xray.
- `vpn:seed`: загрузка кандидата, нативная проверка Xray/Caddy, перенос проверенных файлов.
- `vpn:plan`: проверка томов и конфигурации Terraform, сохранение плана.
- `vpn:apply`: применение сохранённого плана, соответствующего текущим параметрам и содержимому томов.
- `vpn:status`: состояние контейнеров. `running` не означает работоспособный VPN.

После развёртывания проверьте обычный HTTPS без VPN и настоящий HTTPS-запрос через клиентский туннель. Затем — DNS, IPv6, звонки и переключение узлов с Android/iOS/macOS/Windows на реальных сетях родственников. Серверный VLESS не настраивает системный VPN на устройствах автоматически.

## Резервные копии

Храните зашифрованную копию `runtime/<node>/` вне самого VPS и ноутбука. В ней ключи, UUID, параметры узла и Terraform state. Сертификаты Caddy лежат в отдельном постоянном томе; его копия помогает избежать лишнего перевыпуска и ограничений ACME. Terraform volumes Caddy защищены `prevent_destroy`, конфигурационные тома не удаляются Terraform.

State находится отдельно для каждого узла в `runtime/<node>/terraform/`. Это локальный backend; не запускайте изменения одного узла одновременно с разных компьютеров. Для совместной работы позднее нужен удалённый backend с блокировкой и шифрованием. Приватные runtime-файлы нельзя отправлять в issue или чат.

## Замена сервера

1. Переключите клиентов на уже работающий резервный узел. Сам Terraform этого не делает.
2. Подготовьте новый VPS и среду исполнения. Сохраните старый узел до проверки замены.
3. Создайте новый runtime-узел либо восстановите проверенные конфигурации из резервной копии. Не копируйте старый Terraform state как состояние нового VPS: он привязан к прежним ресурсам.
4. Установите корректные DNS-записи. Уберите AAAA, если IPv6 на новом сервере не обслуживается. Для production Caddy нужен доступ к TCP 80 на этом узле.
5. Выполните seed, просмотрите plan и примените его. Проверьте сайт и сам туннель.
6. Раздайте обновлённые клиентские профили. Существующие соединения при смене узла могут оборваться.

Автоматический рестарт `unless-stopped` восстанавливает завершившийся процесс. Он не лечит блокировку IP, отсутствие сети или зависший процесс, который не завершился. Два независимых провайдера и кэшированные профили двух узлов уменьшают зависимость от одного отказа.

## Версии

Xray закреплён по версии 26.3.27 и digest официального multiarch-образа; Caddy — по версии 2.11.4-alpine, Terraform Docker provider — 4.6.0. Обновления нужно проверять отдельно, включая совместимость всех клиентских приложений. Старый pin не гарантирует отсутствие уязвимостей. Метрики, публичные панели, API и access logs в первой версии выключены.
